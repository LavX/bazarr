## Request-host check

- While no login is configured, Bazarr+ answers requests only for hostnames it recognizes: addresses, `localhost`, single-label names and names under `.local`, `.lan`, `.home.arpa`, `.internal` or `.localhost` are always answered, and any other hostname needs an entry under Settings > General > Allowed Hosts (or `BAZARR_ALLOWED_HOSTS` in the environment). The entry can also be added by hand as `allowed_hosts` under `general` in `config.yaml`, which applies after a restart. When such a request is refused, the page it gets names the hostname and offers a one-time approval code: the code is printed to the console Bazarr+ runs in (the terminal, `docker logs` for a container, `journalctl` for a service) and appears nowhere else; each use replaces it, and every restart prints a fresh one. A reverse proxy has to hand Bazarr+ the hostname the client asked for: as the `Host` header it forwards, or as `X-Forwarded-Host` from a proxy named in `general.trusted_proxy`. That hostname has to be recognized, and the proxy has to refuse hostnames it does not serve; a proxy that rewrites the `Host` header to an internal upstream name leaves the address-bar name unanswered, because the rewritten name is the one judged and the address-bar name never arrives. When a forwarded name is believed, it is judged together with the `Host` the proxy sends, so both need to be recognized, and a refusal names the one that failed. Webhooks and plugins that point at a hostname outside this set fail until the hostname is allowed.
