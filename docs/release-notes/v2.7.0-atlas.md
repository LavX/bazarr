# Bazarr+ v2.7.0 (Atlas)

Codename: **Atlas** (opening the v2.7 line).

Bazarr+ v2.7.0, Atlas, is the first feature release after the v2.6 Clockwork line. It changes what the application is for on arrival: Discover becomes the homepage, it works with no library at all, and it can search, preview and download a subtitle for any film or show on its own. Around that it adds Sports as a third media type with Sportarr as an instance kind, folds all four media servers onto one multi-instance layer, gives Statistics a real page of its own, and closes a set of session and container defects that had been live for several releases.

Atlas is also the release where a few things that were quietly missing get written down: PostgreSQL backups now actually contain the database, the container no longer hands the application tree to the runtime user, and a Provider Hub plugin can no longer name itself after one of Bazarr's own settings sections.

---

## Headline: Discover is the homepage, and it works with no library

Discover is a standalone subtitle aggregator. It searches any film or show by title or IMDb identity, browses trending titles, digital releases and recent episodes, optionally matches a title against a copy in the local library, and retrieves subtitles. It works against an empty library, without a Sonarr or Radarr connection, and without the reader supplying any external key (#435).

It is now where the application lands.

### Standalone subtitle search for any title

Title and exact-episode retrieval run behind explicit identity guards: a numbering disagreement or an unresolved external identity cannot silently degrade into a looser search. Browsing and refreshing never contact subtitle providers at all. Provider work happens only on an explicit search, so opening the page costs nothing at a provider.

A search shows parallel provider progress and separates providers that cannot serve this request from providers that are unavailable, which are different problems with different answers (#443). Results use the full page width, and a formatted preview opens directly beneath the selected row. Previews render supported formatting safely and still offer the original text without losing the selected result (#445). Download is a single fetch on an exact row, and an expired result handle recovers explicitly rather than by substituting a different row.

Browser Back and Forward restore a completed search from a bounded session cache without submitting to providers again. The same selection can reuse its completed results, logging out clears the cache, and an expired handle stays expired.

A search the reader walks away from is kept too (#513). A page is filed as its history entry is left, so a page filed mid-search carries no results, and the restore used to overwrite the live state with that empty page. If the provider answer had landed while the reader was elsewhere it was discarded; if it had not landed yet, the generation the restore moved on retired it and the search never completed. Both cost provider calls that this page reserves for an explicit search. A live state for the same search context is now left alone when the filed page holds nothing and the live one holds results or is still searching.

Metadata comes from TMDB through the application's own built-in key over the v3 API, resolved by one shared module that the login backdrops also use, so Discover works with no reader configuration. A reader may still supply their own key as an optional override. The key is present as the outbound parameter and absent from the settings payload, the configuration revision, cache internals, response bodies and logs.

### Results as they arrive, and an honest account of each provider

A search across 36 providers showed nothing until the last one finished, while the progress bar was already reporting a running result count, so the page knew results existed and displayed none of them (#520). The backend only ever published counts: rows were built after the fanout returned, and the handle that makes a row actionable did not exist until then, so the page could not have offered a usable row even if it had wanted to. Rows are built and minted as each provider completes now and published with the observation, and the finished list reuses those same rows, so a handle offered mid-search names the same result in the final snapshot and stays valid until the search completes. The list appends in arrival order and never re-sorts, which is safe because the final order is provider completion order: there is no re-ranking pass. Measured on a real 36-provider install, the first rows appeared at t+6.3s on a search that completed at t+21.2s, and a subtitle was downloaded at t+1.9s with 8 providers still pending. "No results yet, providers are still searching" is a different line from a finished search that found nothing, and searching again leaves the previous finished list up rather than replacing it with one that is still filling, since showing both would offer the same subtitle twice under two ids.

The same search applied one wall to the whole fanout and then reported every future it had not harvested as "Provider search timed out", including providers still queued that never ran at all: a provider measured at 3.4 seconds against its live site was reported as a timeout. Three outcomes replace the one. `timeout` means the provider blew a deadline it owns, `abandoned` means it was still working when the shared wall fired, and `not_started` means the call never reached a worker and nothing was asked. `not_started` takes no cooldown and no health penalty, because counting it would discard whichever providers sort last whenever the provider count exceeds the worker count, which is the original defect in a different costume. Running futures are deliberately not cancelled: `Future.cancel()` cannot reach them, so it would mean killing a pooled worker mid-request and breaking whatever concurrent search shares that client, and a half-torn-down worker is a worse failure than one that finishes and is ignored.

Underneath that, this search path was wired outside every backoff mechanism in the project. The library pool passes a throttle callback and an adoption gate and this pool passed neither, and the title search passed no outcome handler, so the health tracker was read from and never written to. What remained was a flat 60-second retry that ignored the cause, so a site returning HTTP 500 to everyone was re-hit every minute indefinitely. Discover uses the same global throttle table and provider health tracker as a library search now, so a failing upstream backs off with escalating delays under the ceiling that already existed. The retry delay derives from the cause: the server's `Retry-After` first, then the throttle table entry the pool just wrote, then a per-cause floor. A provider's `Retry-After` is carried across the Provider Hub worker boundary instead of being lost at it, where two deadlines exist the later one wins on both sides of the table, and correcting a Hub provider's credentials forgets its authentication throttle immediately rather than leaving that provider skipped for twelve hours. A search whose only events were correct skips is no longer reported as failed.

One subtlety worth recording, because it is the kind that makes a fix look complete and do nothing: attaching an outcome handler makes the fanout run detailed, and a detailed provider call reports failure by returning a result rather than raising, so without translating that the ingest path would have read every failure as a success.

### When an episode and its show disagree

Opening an exact episode link whose episode does not agree with the show it was opened from raised "Show details changed. Refresh this episode before searching." with no way past it (#486). The guard itself is right: a search aimed at a superseded show mapping should be refused, and it still is. Four things around it made it a dead end.

The refresh control refetched only the episode, which was rarely the disagreeing side, and the automatic attempt is latched per parent identity, so it fired once and never again. The effect that rewrites the draft from a freshly fetched episode refused to run while the disagreement lasted, so the state it exists to repair could not be repaired. "Enter episode numbers manually", the escape hatch, was gated on the same flag the warning is about, so it was hidden by the condition that created the need for it. And the comparison was strict equality on five fields, so a payload that omits a nullable id read as a contradiction against one that sends null for it.

Now the refresh control and the automatic reconciliation refetch the show as well as the episode, the repair effect adopts a fresh episode for this link's own show, season and number whether or not it still disagrees, absent and null count as the same absence on the three nullable fields, and the manual path is always available with the season and episode from the link already filled in. One predicate answers the question everywhere, instead of a hand-copied second comparison that coerced differently. An episode whose numbering simply cannot be verified is described in the title's own terms rather than called stale, with no refresh control offered for something there is nothing to refresh into.

### The library hero, and counts that name their unit

The page opened with small local panels and only reached a full-width hero once it crossed into TMDB's feeds, so a reader's own library read as a preamble to somebody else's catalogue. Both halves now open with a hero of the same treatment, and the line between them says which side you are on (#450).

Three things were quietly wrong behind that page, and all three are fixed:

- **Covers never loaded.** Arrival covers were published as the owning arr's own relative path, which a browser cannot reach. Every one returned 404, and an `onError` handler hid the image, so the strip showed placeholders and reported nothing wrong. Covers now go through the image proxy carrying the owning instance, so a cover on a non-default Sonarr is fetched from that server rather than from the default one.
- **Counts named the wrong unit.** `wanted.requirements` counts missing subtitle *languages*, not media. On a real library that meant the page could say "176 missing episodes" when 140 episodes needed subtitles and 36 of them needed two languages, overstating the work by a third. Media counts are now published per kind beside the requirement totals, and every figure names its unit, so the queue total and the per-kind links reconcile.
- **A cold load always broke one feed.** The homepage renders three feeds and asks for all of them at once, while the concurrent job cap was two. The third request was refused in milliseconds without ever reaching TMDB, and the reader was told the feed was temporarily unavailable when nothing had failed. The cap is now the number of feeds one page asks for, guarded by a test.

What the page shows now: a library hero over the fanart of the most recent thing this install fetched, with each arrival taking a ten-second turn; **Still missing**, the queue itself grouped per configured library with its own heading and page, where every missing language starts the same provider search the Wanted page starts; and **Needs attention**, which surfaces throttled providers, disconnected library sync and unreachable root folders. The backend had computed those all along and nothing had rendered them since the dashboard revamp, so they were only discoverable by reasoning about an absence. The panel says nothing while there is nothing to say.

The hero also stays readable when there is nothing to draw it over (#474). In the light theme, when no recent arrival carried a backdrop, the hero's status pill, its schedule line and its "All jobs" link kept the cream ink meant for dark artwork and fell to about 1:1 contrast, which made them invisible. A first run with an empty library is exactly that state. They now take the page's own ink when there is no artwork and keep the cream when there is.

### No library at all: the global half is the page

Opening Discover on a fresh install with no Sonarr, Radarr or Sportarr used to show the crash screen (#468). Two separate problems sat behind that.

The summary was trusted to be a summary. Only a non-2xx answer arrives as an error, so anything that answered 200 with something else, a sign-in page from a reverse proxy, an authentication message, or the app's own `index.html` served where an API route was expected, became the summary and was read for fields it does not have. `useDiscoverSummary` now checks that the body carries the components the page reads and treats anything else as a failed read, and the panels take a partial summary as an unknown state rather than a crash.

The second problem was the page itself: an install with no enabled instance got a hero counting 0 series, 0 movies and 0 episodes, a queue of nothing missing, and a panel of nothing fetched, all sitting above the global catalog it can actually fill. **The library half is now rendered only where there is a library.** Where there is none, the global hero opens the page with one line offering to connect a library. An install with an enabled instance and zero indexed items keeps the half, because the hero is what says a scan is running.

The "read, and not understood" state is derived from `isFetched` rather than `isError`, because a query with no data returns to pending while it refetches and a layout watching `isError` flips panels in and out, where each mount starts the next read. That oscillation was observed before the helper existed.

Three follow-ups finished that state after the release candidate. **The sidebar only offers a library this install has** (#496). `Series`, `Movies` and `Sports` were rendered whether or not the matching integration was connected, with the hidden ones added back as "set up a library connection" entries, so the route's own per-kind gating had no effect on what the reader saw, in the rail or in the mobile drawer. Both render the routes as they are now, per kind rather than all or nothing, so an install running only Radarr gets Movies and not Series. `History`, `Wanted` and `Excluded` were already gated on having any library at all. Nothing that does not depend on a library moves, and Connections stays reachable through Settings.

**The connect-a-library line becomes a notice that can be closed** (#496), remembered on the reader's browser through the same guarded storage helpers the What's New wizard uses, and it sits on one line with its close control instead of 11px above it (#497). **And the "Beyond your library" heading goes when the library half does** (#498). It exists to mark where the page stops describing the reader's own library, so on an install that opens entirely on the catalog it was the one line on the page describing something absent. The section keeps its name for assistive technology either way.

### Feeds that stop re-deriving themselves

On a busy instance the digital and recent-episode feeds reloaded on almost every page load, and their rows rendered without artwork. Three causes compounded (#454):

- **Every TMDB call opened its own connection.** `_request` built a `requests.Session` per call, so a feed's twenty-odd calls paid twenty-odd DNS lookups, TCP connects and TLS handshakes. Under load those setups stalled about five seconds each, and the 12-second feed budget was spent after three or four calls. One pooled connection per host now serves the whole process, with cookies refused so nothing leaves per-response state on a shared object, and one retry for an idempotent GET so a connection the far end closed between calls is not reported as a source failure. Measured: the cold warm-up of all three feeds went from 48 connections and over 100 seconds, never finishing inside the budget, to **one connection and under two seconds**.
- **A partially covered feed was retried like a failed one.** A run that ran out of budget stored what it had verified, and that partial result shared the 30-second retry window meant for a feed with nothing to show. Partial coverage now has a window of its own; a feed with nothing to show still retries in 30 seconds.
- **Artwork was the first thing a spent budget dropped.** Posters were resolved in a single pass after every record check, the pass a budget-exhausted run never reaches. Artwork is now resolved while items are built, from the same cached image configuration.

### Reading the page at 320px, and leaving a title

The helper moves under its input, where it stays the input's accessible description, and the grid declares the tracks the current media type actually has instead of reserving one it never fills: 334px of empty column in episode mode, 453px in film mode. Below 1000px the season and episode pair takes a full second row.

One coarse-pointer media query floors them all at 44px, growing boxes rather than type. Every fine-pointer height is byte-identical before and after, so the settled desktop layout is untouched, and the page grows about 8% at 320px from rows that were genuinely too small to hit.
- **The jobs pill elides instead of clipping, and the toolbar band lost its spare chrome** (#508, #515). ## Request a title in Seerr, from Discover

Discover can show any title, but a title that is not in the library had nothing to do. Atlas adds a request action for readers who run Seerr, Jellyseerr or Overseerr, which share the same request API (#453).

A **Seerr** tab on the Connections page takes a URL and an API key, with a test button that reads back the server name, version and the acting user. The key is encrypted at rest, never appears in a log line, and sits in the same secret tier as the Sonarr, Radarr and Jellyfin keys beside it.

On a Discover title page, next to the existing library badge, the page reports what Seerr knows and offers the matching action:

- not known to Seerr and requestable: **Request in Seerr**, one click for a movie
- a request in flight: **Awaiting approval** or **Processing**, with a link into Seerr
- **Declined** or **Failed**: the action is offered again
- **Some seasons available**: **Request seasons**
- **Available in Seerr** or **Blocklisted**: a badge, no action
- Seerr unreachable: a short notice with a retry
- Seerr rejecting the key: a notice linking to settings, shown once per session

Requests are made as the Seerr owner, which Seerr auto-approves and dispatches immediately. The page says so next to the action rather than leaving it to be discovered.

Shows open a season picker with nothing preselected, separating seasons Seerr already has, seasons this library already holds, and seasons still available to request, so selecting everything cannot re-request what exists. Seasons Seerr already has are plain text rather than disabled checkboxes, so the reason is readable with a keyboard or a screen reader. Where Seerr forbids partial series requests, the picker collapses to a single whole-series action, and a 4K request is offered only where Seerr has a 4K lane and the acting user may use it.

Two details were taken from the Seerr, Jellyseerr and Overseerr sources rather than their API docs, which are stale here: media status value 6 means deleted on Overseerr but blocklisted on Jellyfin-lineage servers, which use 7 for deleted, so capability is detected from the fields a server returns in its public settings and never from a version string; and season status uses the same enum as the media row, so a season at pending, processing or partially available is in flight rather than ready to watch.

The control renders nothing at all when Seerr is not configured, or for a title with no TMDB identity. No schema change, and a failing or absent Seerr affects only the badge on the title page.

## Sports as a third media type

Sports is no longer a parallel implementation beside series and movies. It is a first-class media type using the shared subtitle workflows and views, with **Sportarr** as an instance kind alongside Sonarr and Radarr, and the owning instance preserved throughout (#432).

That covers manual search and download, uploads, subtitle editing and promotion, synchronization, translation, combine, scheduled work, Wanted, History, Excluded, global search and library actions. Settings support global defaults and per-instance overrides, disabled owners are excluded from active work, and Sports library refreshes use the configured Plex and Jellyfin libraries.

Ownership is enforced through asynchronous work, file access, history and provider callbacks rather than assumed at the entry point. A persistent owned recording index moves hashing out of Hub request handling; background scans use bounded batches and retries, and an unknown recording keeps its request retryable until deterministic selection is safe. Wanted eligibility and pagination run in SQL, with release-mismatch flags limited to the selected page.

Event moves require authoritative upstream identity agreement before history and blacklist ownership follow them. A malformed artifact proof leaves the rows untouched, and a cancellation rolls back the complete transaction.

Details that would otherwise have gone wrong quietly: a minimum score of zero is preserved rather than read as unset, legacy translated history with no score stays eligible for upgrades, special query characters round-trip, and callback adaptation preserves legacy positional signatures without retrying callback-body errors.

## One media server layer for Emby, Silo, Jellyfin and Plex

### Emby and Silo arrive as instance kinds

Bazarr+ can talk to **multiple Emby servers and multiple Silo servers**, the way it already supports multiple Sonarr and Radarr instances (#431). Both are new in this release.

When a subtitle is downloaded or uploaded, Bazarr+ asks every enabled destination whose local path mappings cover that file to rescan the item, so the subtitle actually appears in the server. Destinations outside the mappings are skipped silently rather than reported as errors. Each instance owns its enabled state, URL, encrypted API key, TLS verification, path mappings, Silo library choices, pending targets, status and retry action.

`bazarr/media_servers/` holds the shared layer: dispatcher, repository, instance model, path mapping and HTTP. `bazarr/emby/` and `bazarr/silo/` are the per-server clients. Refreshes run on a background worker per server with pending targets, generation tracking and retry, so one unreachable server does not block the others.

**Resolution ladder.** A refresh target is resolved by walking a ladder and stopping at the first rung the adapter supports and resolves. For Emby that is **provider ID, then exact path, then title and year, then a library refresh**. The path rung is the only proof of a single file, which is why it sits where it does.

Silo cannot match on identifiers: its Jellyfin-compatible API returns items with no `ProviderIds` field at all, confirmed against Silo 10.12.0, so there is nothing there to match against. That ceiling is in the compatibility layer, not in Silo itself, and Silo's own native scan does scan a single file. Silo therefore uses the exact-path rung with a library-scan fallback, and Bazarr+ observes that scan to completion, so a Silo refresh is confirmed rather than merely requested. The limitation is recorded where the capability is declared.

Settings live under **Settings > Connections**, with named instance cards, per-instance enable, a Test that runs against the saved key, Edit, Delete, and per-instance status with **Retry pending**.

### Jellyfin and Plex converge onto the same layer

Jellyfin and Plex were the last singletons: one URL and one credential each in `settings.<kind>.*`, called inline from the publication and delete paths, with every failure swallowed into a log line (#466). A server restarting when a subtitle landed was never told about it, there was nothing pending to retry, an unreachable server held up the publication thread, and a user with two Jellyfin servers could register one.

Both become instance rows on the shared layer.

- **Schema.** The shared table gains `refresh_movies` and `refresh_episodes`, which is where the movie and series library updates land, plus a JSON `options` column for what is genuinely kind-specific: Jellyfin's library ids and refresh method, Plex's library section names. Whether an instance refreshes movies or episodes is a property of the instance, not of the server product. Both kind check constraints are widened.
- **Import.** A startup backfill reads the existing singleton settings and creates one row per configured kind, under the same durable one-marker-per-kind, atomic-with-the-row pattern Emby and Silo use, so an upgrade changes no behaviour. Plex needed its own rule for what counts as configured: its `ip`, `port` and `verify_ssl` all ship with non-empty defaults, so composing a URL from them would have created a Plex destination for every user who never opened the Plex settings.
- **Capabilities.** Jellyfin walks provider id, then exact title and year, then its configured libraries. Plex walks the IMDB guid then a section update, which is all it has ever done; no title rung was invented for it. Neither declares the exact-path rung, so **neither needs path mappings**, which is what they have always done and the one thing this must not regress. The requirement is now a consequence of declaring the capability, in validation and in the dispatcher alike.
- **The Plex account owns its row.** Plex is the one kind whose connection is not typed into the instance form: the OAuth flow hands back a token and the server picker hands back a URL. Sign-in, an API key saved by hand, a server selection, both directions of the automatic API-key-to-OAuth migration, and sign-out each carry the account's URL and credential onto its row, recorded by id so a second Plex instance added by hand is never taken over. Sign-out switches the row off and strips the credential rather than deleting it. An update takes a URL only from a real OAuth server address or one somebody configured, so a sign-out resetting the scalars to a loopback default cannot point the destination at localhost at the next startup.
- **Dispatch.** The inline calls are gone. Each of them already sat beside the publication callback that hands the same event to the dispatcher, so removing them converges the behaviour rather than dropping it, and both kinds gain pending state, retry, per-instance isolation and a worker thread that is not the publication thread. A destination the publication cannot reach is skipped rather than queued: a path no mapping covers for Emby and Silo, a media type with no library chosen for Jellyfin and Plex.
- **Refreshing a library on demand.** Retry pending only drains targets that are already queued, so an idle instance had no way to ask a server to re-read itself. Every kind that declares the library rung gains a per-instance **Refresh libraries** action, scoped the way that kind actually scopes: chosen libraries for Jellyfin and Plex, mapping library ids for Silo, mapped roots for Emby.
- **API.** Probing an unsaved connection stops being per kind: one `probe` and one `probe-libraries` route take the kind as a value. The `/api/emby/*` and `/api/silo/*` routes stay for compatibility.

The Connections page renders the same instance list for all four kinds. The form shows path mappings only for a kind that declares them, per-type toggles for every kind, library pickers and a refresh method where they are needed, and says "Plex token" where Plex expects one. The Jellyfin singleton form is gone and its settings section is import-only, so a save cannot write a value nothing reads.

> Plex is converged **for refreshes only**. Its account panel, OAuth server discovery, webhook and Autopulse helpers and the recently-added-date writes still read the scalar settings, because none of those is a refresh, and the scalar keys stay readable. The Jellyfin **refresh all libraries** maintenance button is removed: its endpoint acted on settings a user can no longer edit, and the per-instance **Refresh libraries** action above replaces it.

**Opening the Plex tab no longer moves your server** (#472). Listing your Plex servers used to re-test every connection, pick the fastest, and write it back to configuration as a side effect of opening the page. With refreshes going through the instance row and account features reading those settings, a silent re-pick could point the two at different addresses without anyone choosing anything. Listing is now read-only: the stored connection changes when you pick a server or sign in, and not otherwise. The same implicit rewrite of the Sonarr and Radarr base paths, which turned a stored `/` into an empty string, is gone too.

## Statistics, as a real page under System

Statistics started this cycle as a top-level page with six tabs, folding in the old `History > Statistics` chart rather than deleting it (#448). It then got a second pass, because most of it was a status page wearing a statistics label (#455): three of the six tabs re-implemented System > Status, System > Provider Status and System > Tasks.

What shipped is at **`/system/statistics`**, first in the System submenu. The old top-level route and nav entry fall through to the 404 page, as does `/history/stats`.

A new `GET /api/history/metrics` aggregates all three history tables (series, movies, sports) **in SQL**, over the same timeframe, action, provider and language filters. Five tabs, every one of them plotting something:

- **Activity**: the daily download chart, plus a KPI row of total with media split, per-day average, busiest day, and the share that arrived without a manual search.
- **Providers**: downloads per provider, mean match quality, and **blacklist rate**. A provider high on downloads and high on blacklist rate is the one to turn off, which nothing surfaced before.
- **Quality**: match-score distribution, languages downloaded with `:hi` and `:forced` counted separately, and how each subtitle arrived.
- **Distribution** and **Translator**: the existing panels, reused rather than copied.

Filters moved up to the page, so one row drives every history-driven tab and narrowing to a provider survives a tab switch.

### Where the numbers would have lied

Most of the work here was in not shipping a plausible-looking wrong number, and each of these is pinned by a test that fails if the shortcut is taken:

- **Score is normalised per media type before averaging.** Episodes score out of 360 and movies out of 180, so averaging the raw column reports a meaningless 270 for two perfect matches.
- **`score_out_of` is NULL whenever score is falsy, including a real zero.** Filtering those rows would silently discard the worst matches and bias every quality average upward, so each table's known denominator is filled in instead.
- **Percentages above 100 are legitimate.** A hash match scores 359 on top of other matches against a 360 denominator, so the top bucket is labelled `100%+` rather than clipped.
- **Only actions 1, 2 and 3 count by default.** Uploads and embedded scans are written with a synthetic perfect score and translations carry a score derived from a settings field; including any of them measures configuration, not quality.
- **The daily average divides by the inclusive day count**, matching the number of bars the Activity chart draws for the same window.

> PostgreSQL caught a bug SQLite could not: `CAST(x AS INTEGER)` **rounds** on PostgreSQL and **truncates** on SQLite, so 28.9% landed in histogram bucket 3 on one backend and bucket 2 on the other. It is an explicit threshold `CASE` ladder now, so the same library reports the same histogram either way. The same test file covers the float-division difference and `func.date` returning TEXT on SQLite and a `date` object on PostgreSQL.

Panels that read from lossy sources say what the data cannot say: the failed and completed job deques hold ten entries, so a count of ten renders as **"10+"** and is labelled recent rather than total; expired provider throttles are deleted from disk, so that panel is current state and never a rate; the Provider Hub job log is capped at 200 entries and says so once the cap is reached; the sidecar holds a bounded window of jobs, so its cost is labelled recent jobs only. A null duration renders as a dash rather than `0ms` and is excluded from the duration percentiles, so a job that never recorded one cannot read as instant.

## System: announcements you can read, and a log worth reading

### Announcements get the release notes' shape

The Announcements page was a four column table. Measured against the real feed at 1920px it gave SINCE 79px, so `4 months ago` wrapped onto four lines and read as four separate facts, while ANNOUNCEMENT got 1614px and put one unbroken several hundred character paragraph there, so no row had a scannable line. At 400px the table was 810px wide inside a 400px scroller, which pushed MORE INFO and DISMISS off the screen entirely. It is now a stack of cards in the measure the release notes use, which is the deliberate borrow: the same container, the same card shell, the same badge, title, body order (#505).

A card carries a kind chip, a headline, the age and the body. The kind is derived from the text, because the feed schema is `text, link, hash, dismissible, timestamp, enabled` with no type field, and adding one reaches past this page into the announcements JSON and its parser; it only drives a badge, so a misread is cosmetic. The headline is the entry's lead sentence, and nothing is dropped: the headline plus the body reconstructs the original text exactly, and a lead over 160 characters stays in the body rather than being clamped into a title that would say no more than the wall it replaced. The age is held to one line with tabular figures, which is the direct fix for the stacking. The body is clamped to four lines behind a disclosure, with the clamp decided by measuring the element rather than guessing from a length, so a short entry grows no control that does nothing; the whole entry is always in the DOM and one click from readable. A URL the feed left mid sentence is now reachable, the card's own link is named by its host instead of the word `Link`, and both are underlined because neither is distinguishable from the surrounding text by colour alone. Dismissal behaves exactly as before and moves to the card head, where a close affordance is looked for.

Four follow-ups landed on top of it (#509). **Loading rendered as an empty state**, because the loading flag's only consumer was the table that was deleted, so a slow request showed "No announcements for now" before the announcements arrived; the list draws placeholder cards now. **A card with no headline had no accessible name**, so several long entries read as unnamed landmarks each containing an identically named Dismiss button; the card falls back to the opening of its body, cut at a word boundary. **A link under the clamp stayed in the tab order** although the reader cannot see it, and now leaves it while the card is collapsed and returns when it is expanded. And **a URL containing brackets was cut at the first bracket**, so `https://en.wikipedia.org/wiki/Foo_(bar)` became an anchor to `.../Foo_` while the prose still showed the rest: a link that reads as complete and goes somewhere else. The address now runs to whitespace and is trimmed by counting brackets rather than excluding them, so a bracket the address opened is kept and one that merely wrapped it is dropped.

### Status lists the integrations that exist

System > Status listed Sonarr and Radarr unconditionally, so a fresh install read `Sonarr Version` and `Radarr Version` with nothing beside them, which says broken rather than absent, and it never mentioned a media server at all although a connected server's version is the first thing anyone checks when refreshes misbehave (#521).

A row appears only when that integration is actually configured: the master toggle is on, there is an enabled instance to query, and the endpoint has reported a version. That is the rule Sportarr has used since sports landed, generalised into one per-kind helper the three arr rows share rather than replaced. Media servers join the page as one row per instance, because they are multi-instance: two Embys are two rows, titled `Emby Version (Attic)` when there is something to tell apart and plain `Emby Version` when there is not, keyed by instance id so two instances sharing a name still get two rows. A disabled destination produces no row, an unreachable server says so instead of rendering blank, which was the original complaint, and a connected Silo says it is connected with no version reported, because Silo reports no version anywhere in its API.

Nothing in the tree stores a media server version, so a live probe is the only way to have one, and it is bounded and kept off the request. The status endpoint never waits on a media server: it returns what is cached, immediately. Anything stale refreshes on a small thread pool, deduplicated by an in-flight set, with nothing able to escape the worker. A success caches for ten minutes, since a version is a label rather than a health signal, and a failure for one minute, so a server that recovers shows up promptly instead of ten minutes later. The cache key includes the instance revision, so editing a destination's URL retires the old server's version rather than showing it against the new one, and a saved connection test fills the cache for free, so the common path often probes nothing.

Each entry carries how long its answer can stand, zero while a probe is in flight and otherwise the time left on the cached value, and the page waits that long before asking again. Polling only while an entry said "checking" stopped as soon as every destination had any answer at all, so a server that came back up kept reading "Unreachable" until somebody reloaded the page. And a Plex refresh went through the pooled client, which reads the friendly name and the version once in its initialiser and does not re-read them when listing library sections, so a Plex upgraded on the same URL and token reported its old version until the entry was evicted or Bazarr+ restarted. The probe reads the server's root document over the session that client already holds, so the connection pooling stays and the answer comes from the server rather than from a snapshot of it.

### The log grades its levels instead of flipping one switch

`general.debug` was the only control over what the log held, and it moved every per-library level at once. That coupled the lines a bug report needs to the two loggers that write a line per event, so the file was unreadable in exactly the mode a user is asked to reach before reporting, and the lines that explain a failure were only ever in that same mode (#506).

- **One table, both columns.** Per-logger levels are a single mapping of name to a normal level and a debug level, applied in a loop, with every graded logger named once and both columns filled. `SignalRCoreClient`, `websocket` and `ga4mp.ga4mp` were named in the normal branch only and inherited DEBUG whenever debug was on; `git` was named in the debug branch only and now carries the INFO it inherited in a normal install explicitly.
- **A ceiling debug cannot lift.** `socketio.server`, `engineio.server` and `apscheduler` stop at WARNING in debug mode. WARNING and ERROR are untouched, so a transport or scheduler fault still surfaces. `log.verbose_loggers`, empty by default, names the loggers whose ceiling debug may lift, so the firehose stays available to someone debugging the transport on purpose.
- **The vendored fork is un-muted.** `subliminal_patch` and `subzero` are ours rather than third-party dependencies, and were the quietest loggers in the process at CRITICAL and ERROR, stricter than the ERROR given to foreign libraries. Their floors become INFO and WARNING, which is what puts provider lifecycle into the log a user already has.
- **One line is promoted and none are suppressed.** A provider skipped until a later hour changes what the reader gets, so it moves from DEBUG to INFO. No logging call in `bazarr/` is deleted or downgraded, and no Bazarr+ floor is lowered.

Measured on a replay of one debug-mode day with one UI client connected, driven through the real emit path and a real APScheduler executor rather than a simulation of them: **957,284 rows and 165,916,229 bytes before, 4 rows and 389 bytes after**, with `socketio.server` and `engineio.server` contributing 475,760 rows each. The other half of the trade, per search in a normal install over eight providers returning eight candidates: 0 rows before, 26 rows and 3,439 bytes after. That is roughly two lines per provider and one per scored candidate, which is the signal the file was missing rather than a second firehose.

Two related parts are deliberately not in this release: a size ceiling on the log file, which needs a rollover naming design of its own because the stock handler deletes the earlier size-rolled file of the same day, and a bounded, filterable `GET /api/system/logs`, which changes an API contract and the frontend that reads it.

## Onboarding, rebuilt around intent

The onboarding wizard was written when Bazarr+ could do nothing without Sonarr. That stopped being true when Discover became the homepage, and the wizard had not noticed (#462). - **An intent screen after Welcome.** Two honest paths: run Sonarr, Radarr or Sportarr and have subtitles fetched automatically, or find subtitles for anything with no library. The answer filters the step rail and nothing else. It is wizard-local, no backend setting is written, and the copy says either answer can be changed later in Settings.
- **Every arr step is optional, Sonarr included.**
- **The shell owns skipping.** One source of skippability, one control, one label everywhere. A step that is not optional has no skip and says why in one line: languages, because there is nothing to fetch without a language. Providers started out on that list too, for the same reason, and later in the cycle it gained a skip of its own (#523).
- **Seerr becomes an optional step** beside media servers, reusing the same connection test the Connections page uses.
- **A translator step:** one field, the OpenRouter key, or skip. A filled key also selects OpenRouter as the engine, because the key alone would be inert against the Google Translate default.
- **Provider install attempts every selection.** Picking several providers could install only the first, silently. Every selection is attempted now, per-provider outcomes are rendered with the backend's own failure message, the restart is gated on at least one provider having staged, and the failed subset is retryable in place without re-installing what worked. The restart happens after a countdown the reader can see.
- **The Providers step can be skipped offline.** An install that cannot reach the catalog was stranded with no control to click, because "Install & restart" stays disabled until something is selected. It gained a skip of its own, matching the steps around it (#468).
- **A fresh install reaches the wizard again** (#499). The Discover homepage work replaced `Redirector`'s onboarding branch with an unconditional navigate to `/discover`, so nothing had sent anyone to `/setup` since. The wizard itself was never broken: reaching it by hand rendered all twelve steps exactly as before, and only the route to it was lost. The branch is restored ahead of the Discover one and decides on both the settings read and the instance list, because deciding on either alone sends the wrong install the wrong way and the redirect replaces the history entry, so there is nothing to go back to.
- **One action installs the providers that need no account** (#501). A fresh install showed 62 checkboxes with nothing to say which of them work without signing up for something. The Providers step now leads with `Install 36 recommended providers`, naming the count before it is clicked, and the set is read off the catalog manifests rather than kept in a list here: no signup, an empty `config_schema.required`, and no FlareSolverr or anti-captcha capability declared. It stays right as the catalog changes. The action reuses the existing install run, and the ids that actually staged are added to the enabled providers before the restart fires, so the set is live when Bazarr+ comes back; a partial run enables exactly what installed and reports the rest. The capability rule is deliberately on the safe side of what the button claims, because a manifest says a provider *can* use a helper service and never whether it *must*: OpenSubtitles.org, SubScene, NapiProjekt, Wizdom, Yavka.net, Zimuku and Prijevodi-Online stay off the set although the catalog documents the helper as a fallback for most of them, and remain one tick away in the same list. Found while browser-verifying it and fixed with it: a run writes a row per provider as each install answers, and the step read any row as "installed", so it swapped to the configure sub-stage while the install was still working and the outcome report and the restart never rendered. Only a row with a loaded version counts now, which fixes the hand-picked path as much as the new action.
- **Media servers: one picker, then a screen per server** (#502, #518). The step was a Plex tab and a Jellyfin tab, each with its own inline state, so switching kinds discarded anything already typed, and it asked Plex for a hostname, a port and a pasted token, a path the app moved off when Plex gained its account flow. Emby and Silo were absent although both are first-class kinds on the shared instance layer, and the step was gated to the library path, so a Jellyfin user with no Sonarr never reached it at all. Only the wizard ever said one server: the instance table has no uniqueness on name or kind and the Connections page has always rendered as many as you have. It is now one picker where the reader ticks every kind they run, with `Add another` for a second server of the same kind and names auto-numbered so two Embys are not both called "Emby", followed by one configure step per selected server. Each kind's card carries its own state in a footer: the servers already connected, how many are still to set up, its own `Add another`, and Plex's one-account note. Selection lives above the step list, so walking Back into the picker keeps it, and the wizard cursor became a step key rather than an index, because the list grows and shrinks while the reader walks it. Emby, Jellyfin and Silo save through the writer the Connections instance form uses and reuse its editors, labels and URL rule, so a row made here is one Settings can re-save, and the wizard refuses an enabled Emby or Silo with no mapping in the same words Connections refuses it.
- **An untouched arr step writes nothing** (#518). Pressing Continue on a Sonarr step nobody had filled in posted an instance with an empty address, no API key, enabled and default, and then turned the master switch on. The backend accepts it, because only port and timeout are range-checked and the blanks are coerced to `127.0.0.1` and an empty string. The library path shows that step three times, so three clicks produced three enabled instances pointing at nothing, each scheduled for sync and each a permanent health warning, and the Finish screen reported "Sonarr connected". An untouched step reads `Continue without Sonarr` and issues no request, a touched one requires an address, a valid port and a key with each message on its own field, and `is_default` leaves the body entirely because the repository already promotes the first enabled instance of a kind. Test is gated on an address and a key, so it can no longer report a verdict about a server nobody named.

## Translator: SmartFast routing and reliability

### SmartFast and explicit OpenRouter provider routing

Two OpenRouter provider routing choices join the AI translator settings (#434):

- **SmartFast** sends `provider.sort = smartfast`, and the service balances the fastest healthy endpoints against price on its side. Measured in the September benchmarks, plain throughput routing repeatedly resolved to endpoints priced around twice the cheapest that served the same model.
- **Custom** sends the chosen, ordered slugs as both `order` and `only` with `allowFallbacks` disabled, so a job never lands on an endpoint the user excluded. The provider picker reads OpenRouter's public endpoint metadata for the selected model and lists availability, quoted prices and recent median throughput.

**Existing installs keep their current routing.** The setting first shipped in v2.6.2, so a config written before that has no routing key. A genuinely new install (empty config) takes SmartFast; a config with content but no routing key keeps `throughput`, which every translator version serves; a config that already names a usable routing keeps it. A stored value outside the supported set also falls back to `throughput`, because a value that cannot be parsed is not evidence about which translator version is running.

SmartFast needs AI Subtitle Translator 2.0.0 and Custom needs 1.3.4. A version that is read and is too old is refused with a message naming the version to install, and the refusal reads a fresh version so a user who updates and retries is not answered from a stale one. A version that cannot be read is not treated as an old one, since `/health` may be hidden behind a proxy while the job API works: SmartFast degrades to the plain sort and logs it, while Custom still refuses, because degrading would send the job somewhere the user excluded.

### Reasoning that is actually disabled

Selecting **Disabled** previously sent `reasoning: null`, which leaves the model's default reasoning behaviour active and could time a translation out while it generated reasoning tokens. It now sends `{"enabled": false}` explicitly, with a regression test on the outgoing request (#456).

A follow-up closed the gap beside it (#457). The validator pinning the reasoning setting runs only at startup and `save_settings` never re-validates, so a save that clears the key left an empty string in the running config until the next restart, which sent `{"effort": ""}`. The translator service ignores an empty effort, so no `reasoning` key reached OpenRouter at all and the model's own default ran: exactly the failure the selector exists to prevent. Any empty value now falls back to the documented default and sends the explicit disable flag.

### Progress that survives publication

Three translation-notification defects are fixed (#458):

- **Translation status stays visible through publication.** The reducer ended a translation notification the moment progress reached its count, but the sidecar is still finalizing at that point and the file has not been published yet. Completion is now owned by the explicit delete event.
- **Simultaneous jobs get independent notifications.** The progress id was derived from the destination file, so several operations writing one destination shared a single notification and ended each other's. The id is unique per run now.
- **The notification is always cleaned up.** A context manager owns it across submission, polling and every exit path. The six scattered `hide_progress` calls it replaces each missed at least one exit, and a host-job cancellation missed all of them, leaving a dead toast on screen.

Costs and token rates are reported precisely: a real cost is no longer rounded to `$0.00`, and no duration is fabricated when the server reported none.

## Backups, and the PostgreSQL hole in them

A PostgreSQL install wrote a backup archive holding `config.yaml` and nothing else, because the routine only copied the database when PostgreSQL was disabled (#465). The archive still appeared in the backups list, and restoring it was refused as a partial backup, which is the kind of thing an operator finds out on the day they need it.

- **PostgreSQL backups contain the database.** `pg_dump --format=custom` writes `bazarr_postgres.dump` into the archive beside `config.yaml`. The connection is resolved the way `app.database` resolves it, the `POSTGRES_*` environment variables winning over `config.yaml`, and the password goes through `PGPASSWORD` rather than a command-line argument any process on the host can read. `--no-password` is passed so a wrong or missing password fails instead of blocking on a prompt nobody can answer.
- **A PostgreSQL backup without `pg_dump` fails loud.** The check runs before the job is queued, so `POST /api/system/backups` answers 500 with a message naming the missing tool and the package that provides it, instead of queueing a job that dies out of band. No archive is written at all, and the scheduled backup logs the same thing.
- **The image ships the client tools**, so a normal install never meets that refusal path.
- **Restore aborts rather than half-applying.** A failed database copy used to be logged while execution carried on to the restart, so the instance came back with the new configuration sitting beside the old database. On both engines the configuration is staged first, the database goes in second, and the configuration is only swapped into place with `os.replace` once that worked. Any failed step aborts before the restart with nothing half applied, and the staged files are cleared so the next start does not silently retry. An archive that does not contain the database for this instance is refused in `prepare_restore`, before the restart, rather than at the next boot.
- **A restore reports the success it is** (#470). The restore request used to close the server and exit the process on the request thread, so the success response never left, and the container's own supervisor proxy answered 503 for the dropped upstream. The restore had already worked, and the page said it had failed. The request now answers with a restart notice and schedules the restart after the response is on its way.

## Security

### Session and event-layer hardening (#451)

Four defects in the session and event layers, live since form login shipped, plus the cookie policy they all argue for.

**One failed login unlocked four routes.** `check_login` asked whether the session carried a `logged_in` key, and a failed login wrote that key with the value `False`, so one wrong password produced a cookie that satisfied the gate. That opened `/bazarr.log`, `/system/backup/download/<name>`, and both cover-art proxies, none of which has a second gate. The backup is the serious one: `config.yaml` carries the secrets master key in clear, so the archive is every credential in the install, decryptable, and backup names are date-stamped and guessable. Both gates now call one helper that compares against `True` identity rather than truthiness, and a rejected login removes the key instead of storing `False`.

**The admin's plaintext password was written into the browser cookie.** Installs adopted from upstream Bazarr store the password as MD5, so this fork verifies MD5 and re-hashes to PBKDF2-SHA256. That re-hash was deferred by putting the submitted plaintext into the session under `_pw_for_upgrade` and waiting for the browser to call back. The session here is a signed, unencrypted cookie with no server-side store, so the password went to the browser, stayed in the cookie jar, rode along on every later request, and reached any proxy log that records cookies. On a plain-HTTP LAN install it also crossed the wire in the clear. The plaintext is already in hand in the success branch, so the upgrade happens there: the deferred token, the client round trip and the prompt modal are gone, and login answers 204 with no body.

**CORS was unconditionally on.** The switch read `settings.get('cors', 'enabled')`, which reads like "the enabled key of the cors section" but is dynaconf's `get(key, default)`: it returns the section, `{'enabled': False}`, and falls back to the string `'enabled'`. Both are truthy, so every route answered with `Access-Control-Allow-Origin: *`, including the unauthenticated login endpoint.

**The event socket had no gate at all.** Same defect class, worse in effect. The socket was configured with a wildcard origin, so engineio reflected the caller's origin and added the credentials header, and there was no connect handler, so the gate that protects every other surface did not exist here. Anyone who could reach the port, from any page in any tab, could open a long poll and watch the whole live library and task event stream with no cookie and no API key. Origins now follow the same switch the HTTP routes obey, defaulting to engineio's same-origin mode, which derives the allowed origin from the request's own scheme and host and honours forwarded headers so a reverse-proxied install keeps working. A connect handler refuses the connection unless the handshake proves who it is, accepting either the session cookie or the API key from the connect payload, and it is wrapped so an error refuses rather than admits.

**Cookie policy, lifetime and trusted proxies.** The cookie was issued with Flask's bare defaults: no `SameSite`, no `Secure`, no expiry. `SameSite=Lax` and `HttpOnly` are explicit now. `Secure` is a policy rather than a flag, because one answer cannot serve an instance reached both ways: `auto` (default) follows the scheme of the request the cookie is set on, decided per request, with `always` and `never` as overrides. Lifetime uses `session.permanent` with `PERMANENT_SESSION_LIFETIME` so the signature expires too, default 30 days and configurable, re-issued on each request so it is an idle window rather than an absolute cap. `general.trusted_proxy` (default `127.0.0.1`, the in-container supervisor hop) replaces the hardcoded waitress value: a reverse proxy in another container was not believed before, so its HTTPS read as plain HTTP and every visitor on the internet shared one login rate-limit bucket. It is one address rather than a list, because waitress compares the peer against the value exactly.

### A plugin can no longer claim a Bazarr settings section (#460)

Provider Hub manifest validation checked a plugin's `provider_id` against the provider registry and nothing else, so a catalog plugin could call itself `sonarr`, `plex`, `auth`, `proxy`, `postgresql` or `translator` and install cleanly.

The pool overlay in `get_providers_auth()` then copies every key the plugin declares in its `config_schema` out of the settings section named after the plugin. Settings are decrypted in memory, so a plugin with `provider_id: sonarr` and a declared `apikey` was handed the Sonarr API key in the config shipped to its worker on every search and download. The same for `plex.token`, `auth.password` and `postgresql.password`. Nothing in the install path, the bundle hash checks or the smoke test noticed, and a test asserting that the worker only receives declared keys stays green, because every leaked key is declared.

`validate_manifest` now rejects a `provider_id` that names one of Bazarr's own top-level settings sections, for every install source, trusted catalog and local upload alike. The reserved set is derived from the settings validators at validation time rather than hand-kept, so a section added later is covered the day it is declared, and sections a subtitle provider owns are subtracted, because a catalog plugin replacing a built-in reuses that built-in's id and settings section on purpose. Deriving from the validators rather than from the stored settings is load-bearing and covered by a test: saving a plugin's Settings card writes its config under the plugin's own id, so reading the stored sections back would make a plugin reserve itself out of the pool the moment its user configured it. The overlay carries the same check and falls back to the plugin's own stored config and schema defaults. No behaviour change for any legitimate plugin.

### The connection tests stop echoing whatever answered (#479)

Both connection-test proxies answered a 200 handshake by reading `result.json()['version']` and putting it straight into the response body. The caller picks the host, so those bytes are caller influenced: any length, any type, any content, no validation. Exploitability was low, because the routes sit behind the login gate and the proxy API key and the body is serialised as JSON, but nothing in the code made that true. Both routes exist to read one version string out of a Sonarr or Radarr style handshake, so both are constrained to that now: an object body, and a version that is a non-empty string of at most 64 characters made of characters a version can contain. CodeQL flagged only the legacy route, but `/test/<service>`, the one the settings page and the setup wizard actually call, had the identical echo and gets the same treatment. The response contract is unchanged, and the service route still records a failure and tries its remaining status paths rather than returning a verdict, which matters because Sonarr and Radarr are probed on the legacy path before the v3 one.

### The container no longer hands over the application tree (#464)

`docker/entrypoint.sh` chowned `/app/bazarr` to `PUID:PGID` before dropping privileges, so every process running as that user could rewrite the `.py` files the host imports on its next restart. That included each Provider Hub worker, which is why the worker subprocess was only ever a fault boundary and never a security one.

- **Entrypoint.** Chowns `/config` only. Drops to the numeric `PUID:PGID` rather than to the `bazarr` user name, because `usermod` and `groupmod` rewrite `/etc`, which `read_only` mounts read-only, and going by name would silently have left everything running as UID 1000 when the rename failed. `HOME` is passed explicitly, since gosu takes it from the passwd entry. The `/config` chown warns instead of aborting when it fails, so an operator who pre-owns `/config` and drops `CAP_CHOWN` entirely still boots.
- **Binaries move to `/config/managed/bin`.** The old location beside the application is still read, so an upgrade keeps binaries it already has instead of downloading them again. `binaries.json` lists ffmpeg and ffprobe, which is the whole of what this downloader manages; unrar and alass come from the image or the operator's PATH.
- **Image.** No longer creates `/app/bazarr/bin`, and asserts at build time that nothing under `/app` is owned by anyone but root or is group/other writable. `.dockerignore` only excluded top-level `__pycache__` and `*.pyc`, so a local test run put every nested one into the build context and the image shipped bytecode compiled on somebody's laptop, in a tree nothing can refresh.
- **The in-app updater is gated off in the image.** `main.py` called `apply_update()` unconditionally, outside the no-update gate, and `/config` outlives the install that wrote it, so a directory carried over from a source install could still hold that install's queued release. Against a writable tree that unpacked the stale release and the update cleaner then deleted every file the archive did not contain. Startup now calls `install_downloaded_update()`, which unpacks only when this install is the one that updates itself, and otherwise discards the archive with a single line saying why.
- **Hardened reference compose.** `read_only: true`, `tmpfs: [/tmp]` capped at `size=512m`, `cap_drop: [ALL]` and `security_opt: [no-new-privileges:true]`. Three capabilities come back, because the startup needs `CHOWN` to hand `/config` to `PUID:PGID` and `SETUID`/`SETGID` to become that user, and gosu fails outright without the last two. A bare `cap_drop: [ALL]` does not boot at all, which is a dead container rather than a hardened one. After the drop, Bazarr+ and every Provider Hub worker run with no capabilities. The README, the install guide and the one-liner installer all carry the same keys now, and the guide documents the same as `docker run` flags and notes that mounting a source tree over `/app/bazarr` needs `read_only` dropped.

## Other Improvements & Fixes

- **Editor keep-all sync previews now have a destination they own** (#463). The timing panel submits an alignment with no output mode, so `/api/editor/sync` defaulted it to `keep_all` and wrote its input to a system temp file whose name is unrelated to the video's stem. The ownership check then always answered no, and the keep-all branch appended `destination_ambiguous` for every engine before a single one ran, which the editor worker turned into a failed job. Overwrite previews worked because overwrite never enters that check, which is why only the default request failed. Previews now open a private workspace directory, recognised by the directories this process actually opened rather than by name, and its delayed cleanup discards the whole directory, engine outputs included. Publication is unchanged: a preview writes no library sidecar and emits no media-server refresh.
- **Settings edits survive a refresh that lands mid-edit** (#461). Opening a settings page and changing something before the refresh that follows the first socket connection had finished threw the change away: the form was reset whenever any settings refetch ended, so the staged value reverted, the pending-change warning and the floating Save control disappeared, and no settings POST ever happened. Every reconnect refresh did the same. The form is now cleared only on the reload that follows a successful save. The settings modal carried the same reset with no exception at all, and gets the same rule.
- **Combined subtitles keep their encoding, and translation status stops going stale** (#447). Valid UTF-8 and BOM-marked Unicode are preserved when combining, with encoding detection used only as a fallback for legacy files. Movie subtitle badges are derived from the current file lifecycle, so replacing or deleting a subtitle clears a stale translated flag while a later synchronization preserves a current one. History APIs expose stable event IDs and timestamps for deterministic ordering. Fixes https://github.com/LavX/bazarr/issues/442 and https://github.com/LavX/bazarr/issues/444.
- **Editor HLS playback works for an explicitly selected instance** (#446). The playlist URL includes `arr_instance_id`, but its relative initialization and media URLs lost that parameter, so those requests selected a different stream cache and returned 404 while the playlist itself kept loading. The validated instance ID is carried into the initialization and media URLs in the manifest, preserving native HLS API-key encoding and existing unscoped playback.
- **The running version is in the page title** (#449). Document titles ended at the instance name, so a tab read `Series - Bazarr+` with no way to tell which build was running. Every title now ends with the version, through one `useAppTitle()` hook all 18 call sites use. Discover set no title at all and, being where the app lands after login, showed the static fallback until you navigated elsewhere. The base is still the `instance_name` setting rather than a hardcoded string, so a custom name is followed.
- **The Jobs icon stays visible while jobs run** (#452). While anything was running or queued, the Jobs entry in the navigation rail swapped its checklist icon for a stack of up to three thin progress bars. With one running job and one queued that stack rendered a single animated amber dash plus an invisible zero-width track, so the entry lost its icon and read as a stray stripe floating above the label. The icon stays put in every state, with activity as a single 18x3 stripe under it: transparent when idle so nothing shifts when a job starts, an empty groove when queued, an indeterminate sweep when progress is unknown, and an amber fill at the real percentage when it is known. Reduced motion pins the indeterminate stripe to a dim full bar. The stripe averages the running jobs and only claims a percentage when every running job reports one, because presenting one job's 80% as the state of the whole button was not true.
- **Catalog refresh distinguishes a rate limit from access denial** (#445), keeps cached entries and the last successful check on failure, and offers an in-place retry. Automatic reads initialize only never-attempted sources, so a failed first refresh does not cause repeated network requests.
- **Narrow Status layouts, production login blur and obsolete Discover styles** were fixed in the same pass (#445), with the accepted 40px controls preserved and the existing action colours shared across buttons.
- **Manual and translated subtitle upgrades are separate switches** (#476). Translated subtitles shared the upgrade toggle with manual downloads, and that toggle defaulted on, so the upgrade job replaced a translation with a provider listing every cycle even when the score did not improve, which hammered OpenSubtitles. Settings > Subtitles now has **Upgrade Manually Downloaded or Uploaded Subtitles** and **Upgrade Translated Subtitles**, both off on a new install. See the upgrade notes for what an existing install keeps.
- **A translated subtitle stopped being upgraded forever** (#507). A reader's notification cards showed the same OpenSubtitles listing for the same film, same provider, same score of 74.44%, twelve hours apart, until Bazarr+ was stopped to halt the traffic. Nothing was wrong with the listing: the same subtitle was being downloaded again rather than a better one appearing. The upgrade baseline is the newest history row for a video, language string and instance, and a translated row is always a candidate because it carries half the scale or no score at all, so any real listing beats the bar it sets. The upgrade then writes its result under the language the provider returned, which for a profile that prefers HI is a different variant string: the translation is `nl:hi`, the provider result lands as plain `nl`, and no second row ever reaches the `nl:hi` group. The translated row stays that group's newest row, the file it points at was just removed by the upgrade itself, and the wanted scan's "already translated" guard only holds while that file exists, so the language is translated again and the next cycle fetches the identical listing. A translated row is no longer a candidate once a provider-sourced row exists for the same video, instance and language, with the `:hi` and `:forced` variants compared in Python because no portable SQL expression for it reads the same on SQLite and PostgreSQL. A translation is therefore replaced by a real subtitle once rather than once per cycle, while a strictly better listing still upgrades, because the provider row keeps its own score as the bar. The re-translation guard no longer fails just because the upgrade deleted the translated file either: a provider file on disk for that language ends the question, counted the same way the missing subtitle list counts it, so a `:hi` file covers a plain entry and a `:forced` file does not.
- **A failed search or download says why** (#484, #487). The reason was never lost. The manual search and download paths return the failing stage as a sentence, and the sports routes caught it as a bare `except OSError:` and replaced it with a constant pointing the reader at the recording and the providers. In the reported case the file was fine and the provider had answered; the real reason, `Downloaded subtitles isn't valid. Check log.`, was in the log the whole time. Both routes surface the sentence now and keep the constant as the fallback for an argument-less error, so the body can never come back blank, with the status code and the response shape unchanged. The browser then discarded it too: the request layer deliberately raises no notification for 409 and 412 and sets the message from the body, and `ManualSearchModal` caught the error without reading it and rendered `Download failed. Search again and retry.` A subtitle that arrived and could not be used and a provider that was throttled read as the same shrug, and those ask for different things. The modal is opened by episodes, movies and sports, so all three stop hiding the reason together.
- **The header band has one owner for its surface** (#485). Content scrolled under a transparent band, so a section heading passed through it and landed on top of the page title, on every page long enough to scroll and worst at phone width where the band is two rows and 134px tall. Two rules set the background, both carrying `!important`, and the two-class module selector outranked the one-class global rule written for this exact symptom, whose own comment records the earlier diagnosis: a page title read "ver". So the frosted ground that rule added had never been in effect. The module owns both scroll states and the fade between them now, and the losing rule is deleted rather than left to lose silently again. The scrolled state takes the band's own ground colour at 97% instead of the content surface at 72%, so the surface no longer depends on a blur to hold content apart from the title. At rest the band is still transparent, by design, and the rendered frames at scroll zero are pixel-identical before and after at both widths in both themes.
- **An episode row with dozens of subtitle tracks is readable** (#495). One episode in the reported library carries 46 entries, 2 files on disk and 44 tracks inside the container, and Apple TV+ WEB-DLs run past eighty. The row drew every one of them in a single no-wrap line, and flex items shrink, so past a certain count each badge was squeezed below the width of its own label: the column read as a row of single letters and pushed the table wider than its container. Three changes that only work together: the external files come first, because they are the entries a reader can act on and an overflow must never be what hides them; badges keep their labels and the line wraps instead of compressing; and twelve show with the rest behind a count that opens, so one episode cannot own the page. The cell went from 1302px to 848px, and the table from 1670px inside a 1428px container to 1428px with no horizontal scroll. This one is inherited rather than from this cycle: the no-wrap arrived with the Mantine v7 upgrade and is present in v1.4.4.
- **The leave prompt's buttons get one row, or a real column** (#500). The prompt offered three ways out in a group that wraps by default, so at the dialog's width the third dropped onto a line of its own and the same choice was presented twice, as a pair and a stray. Forbidding the wrap alone was not a fix: three 44px targets carrying these labels need roughly 370px and the dialog body is nearer 288px at a 320px viewport, where these buttons are the only way out of the prompt. They share a row while it fits and stack full width under it, keeping source order, so what a sighted reader sees and what the tab key walks stay the same sequence.
- **The site and the README stopped assuming a library** (#483, #511, #481, #482, #504). The landing page promises Bazarr+ runs with no library at all, and its "Start here" button pointed at a getting-started guide that contradicted the promise in its second sentence and described a wizard that no longer exists. That guide now states the two ways to run Bazarr+, keeps a media stack optional, gains a "Running with no library" section ahead of the Sonarr and Radarr one, and describes the wizard that actually opens. The Getting Started card on the guides index, the last place on the site still telling a reader a library is part of getting started, names all three library sources and the no-library path. The README and the site copy say what Atlas ships, and the site drops a fourth ink level along with a token that could not meet AA (#503).
- **Language profile lookups that crashed uploads and indexing** are guarded (#433).

## Upgrade / Migration Notes

Pull the new image and restart. Schema migrations run on boot and existing settings, language profiles, providers and instances carry over. **PostgreSQL remains fully supported and first-class**, and every migration in this release is covered on both engines.

A few things need a closer look.

**1. Jellyfin and Plex become instance rows on the first startup.** The startup backfill reads your existing singleton Jellyfin and Plex settings and creates one instance row per configured kind, once, under a durable marker. Nothing to do, and nothing changes about how your servers are refreshed. Three consequences worth knowing:

- The **Jellyfin singleton form is gone.** Jellyfin is edited as an instance under **Settings > Connections** like the other three kinds, and its old settings section is import-only, so a save cannot write a value nothing reads.
- The Jellyfin **"refresh all libraries"** maintenance button is **removed**. Its endpoint acted on settings you can no longer edit. Use the per-instance **Refresh libraries** action on the instance card instead, which is available on every kind that declares the library rung.
- **Plex is converged for refreshes only.** Its account panel, OAuth sign-in, server discovery, webhook helper, Autopulse generator and recently-added-date writes still read the scalar Plex settings and are unchanged. A Plex row is created only where Plex was genuinely configured, because `ip`, `port` and `verify_ssl` all ship with non-empty defaults and composing a URL from those would have created a destination for every install that never opened the Plex settings.

Neither Jellyfin nor Plex declares the exact-path rung, so **neither needs path mappings**, exactly as before. If you have two Jellyfin servers, you can now register both.

**2. Everyone is signed out once.** The session cookie's semantics change, and login clears the session before marking it, so a cookie from an older release cannot carry its stored password forward. Sign back in as usual.

Three settings behind that change are read when the application starts, so **changing them needs a restart**, and the settings page says so: `auth.session_lifetime_days`, `auth.cookie_secure` and `general.trusted_proxy`.

- If you reach Bazarr+ through an HTTPS reverse proxy that this instance cannot detect, set `auth.cookie_secure` to `always`. The default, `auto`, follows the scheme of the request the cookie is set on.
- `general.trusted_proxy` defaults to `127.0.0.1`, the in-container supervisor hop. It is **one address, not a list**, because waitress compares the peer against the value exactly. If your reverse proxy runs in another container, set its address here so forwarded headers are believed and per-visitor login rate limiting works. Clearing the field means trust nothing.
- Operators who left CORS disabled will stop receiving an `Access-Control-Allow-Origin` header they may have been relying on without knowing. That is the documented behaviour of the setting; turn CORS on deliberately if you need it.
- The legacy password upgrade is now silent rather than prompted. The prompt it replaced carried a warning worth repeating: **once an MD5 password is upgraded to PBKDF2, going back to upstream Bazarr means resetting the password in the config file.**

**3. If you run a custom compose file, compare it against the reference.** The shipped compose, the README block, the install guide and the one-liner installer now set `read_only: true`, `tmpfs: /tmp` capped at `size=512m`, `cap_drop: [ALL]`, `security_opt: [no-new-privileges:true]`, and add back exactly three capabilities: `CHOWN`, `SETUID` and `SETGID`. A bare `cap_drop: [ALL]` does not boot, because the entrypoint needs those three to hand `/config` to `PUID:PGID` and become that user. Nothing forces you to adopt the hardened keys, but the reference is what the project supports.

Two related changes land with it. Managed binaries move to **`/config/managed/bin`**; the old location beside the application is still read, so an upgrade keeps the binaries it already has. And the **in-app updater is gated off in the image**, on two independent switches. Update by pulling a new image, which is what the Docker install has always meant. If you mount a source tree over `/app/bazarr` for development, drop `read_only`.

**4. PostgreSQL backups need `pg_dump`, and the version has to match.** The image ships `postgresql-client`, so a normal install needs nothing. If you run from source, install the PostgreSQL client tools: without them, `POST /api/system/backups` answers 500 naming the missing tool rather than writing an archive that turns out to be useless.

**Version skew matters.** The `pg_dump` client major version must be at least the server's major version. A client older than the server refuses the dump. If you run a PostgreSQL 18 server, back up with an 18 or newer client.

Any backup you took on PostgreSQL before this release **does not contain your database**. Take a fresh one after upgrading. A restore now aborts before the restart if any step fails, leaving nothing half applied, and an archive without the database for this instance is refused before the restart rather than at the next boot.

**5. Existing installs keep their OpenRouter routing.** The new SmartFast default reaches genuinely new installs only. A config that predates the routing setting keeps `throughput`, which every translator version serves, and a config that already names a usable routing keeps it. If you want SmartFast, select it in the AI translator settings; it needs AI Subtitle Translator 2.0.0, and the Custom picker needs 1.3.4.

**6. Translated subtitle upgrades are off after this upgrade.** The combined upgrade toggle is split in two (#476). An existing install keeps its manual-upgrade setting as stored, or on if the key was missing, and gets translated upgrades off; the old combined value is not copied onto the new switch. If you relied on translations being replaced by provider subtitles, turn **Upgrade Translated Subtitles** on in Settings > Subtitles.

**7. The log file changes what it holds, in both directions.** Per-logger levels are graded rather than flipped by one switch (#506). A normal install gains the provider lifecycle lines that explain why a search found nothing, roughly two per provider and one per scored candidate, which is what makes a log worth attaching to a report without turning debug on. Debug mode loses the per-event firehose: `socketio.server`, `engineio.server` and `apscheduler` stop at WARNING there, so faults still surface while the flood does not. If you are deliberately debugging the transport or the scheduler, name those loggers in the new `log.verbose_loggers`, which is empty by default.

One more note for a fresh install: **Discover now opens without a library**. If you have no Sonarr, Radarr or Sportarr instance, Discover is the whole page and the library half is not rendered, with one line offering to connect a library when you want one. The onboarding wizard asks which of the two you are before it builds its step list, and Sonarr is no longer required to finish it. The wizard is reachable again from a fresh install's first load (#499), its media server step takes every kind you run and gives each server a screen of its own (#502, #518), and its Providers step leads with a single action that installs every provider needing no account (#501).
